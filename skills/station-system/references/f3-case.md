## 配置快照

| ID | 类型 | 名称 | postion(mm) | isAccurate |
|---:|---|---|---:|---|
| 12 | P2P | 起点 | 1 | false |
| 77 | MUST | 创建任务 | 2010 | false |
| 56 | TASK | 梁长-首 | 7000 | false |
| 16 | MUST | 过车头点 | 2000 | true |
| 17 | P2P | 靠近梁 | 14430 | false |

ID16 启用动作：驱动100/100、distance1000 -> 等待4000ms -> 路径4区间检测（X0～500,Y1000～2000,Z1900～3000,checkType0）-> 沿路径4前进350 -> 等待3000ms -> 设置机器人位置到点56。

ID56 启用动作：开始尺寸检测 -> 路径4区间检测（X50～4000,Y0～3000,Z-300～-100,checkType1）-> 等待3000ms -> 设置机器人位置到点17 -> 手动录入(pid5263,value1)。其他截图行未勾选，不当作实际执行。

路径4来自动作参数，尚未用部署 NavPoint.pid 验证 F3 的真实路径 ID。不能仅凭路径名称断言两者一定一致。

## 与初次看图分析相比，需要修正的结论

1. No 是显示行号，不能据“ID56在ID16前一行”判定会先跑56再跑16。源码按路径sequence/里程安排目标，并补入MUST。
2. 设置位置确实写路径及里程原点，不是前往该点。ID16 完成后预期逻辑位置跳到7000，而非仍在2000。
3. “精确修正”确实存在短暂反向驱动，但要先看到补偿日志，不能用它解释所有起点倒退。
4. 启用点不等于每个点都作为顶层目标。必须拿到真实任务目标及P2P映射。

## 源码支持的候选过程

假设：现场使用 RobotNavDevice、已在同一路径起点附近，当前小于2000；下一个顶层目标是77(2010)，或者是56(7000)且规划区间包含16/77；启用项与截图一致。

规划去77时，严格区间包含16(2000)，子路线可为：`16 -> 77`。执行16的定位及动作后，它调用 setRobotAtThisPoint(56)，把逻辑里程设为7000。子路线中的77不会被自动删除。接着定位77时，`当前7000 > 目标2010`，fixPostionPreAction 选择后退。

若直接规划去56，子路线可能为 `16 -> 77 -> 56`，同样存在16重设里程后仍去77的衔接问题；如果16还作为顶层目标被显式选中，可能有不同的重复访问过程，需以实际队列为准。

这是配置与调度机制组合形成的候选原因，不是已证明故障。“到F3起点1就后退”若发生在ID16动作之前，不能套用上述过程，优先查看路径关联映射、路径前置动作、PLC当前坐标和目标点。

## 现场应核对什么

- 任务或手动入口实际传入的 pointIdList，路径 sequence、point.pid、启用状态。
- 到达F3起点时PLC pathId/路径原点/当前里程，是否刚发生NavPointMap转换或设置位置。
- 日志里16和77实际先后，以及设置到56之后的下一个目标。
- 出现倒退时有没有“机器人执行后退消除缓停里程”；若有，其目标点ID与误差是多少。
- 路径前置、起点P2P映射、DeviceObserver、命名脚本或线程动作组中是否另有显式驱动。
- ID16 的驱动1000和随后固定等待4000ms，是否与实际完成位移一致；下发距离指令并不自动等价于阻塞等待走完。

确认业务要求后再改：若必须先创建任务，应确保它在重定位动作之前执行，并重新检验其MUST里程和规划区间。可讨论将创建任务纳入明确的前置链，或调整点位职责/坐标；没有物理参考和配置导出时不给武断的新里程值。起点1改0、或把16机械地改到7000之后，都没有现成源码证据支持。
